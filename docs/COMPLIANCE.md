# 合规与法律风险边界

> 本文件用于说明需要关注的合规问题和本项目的技术护栏，**不是法律意见，也不保证任何具体使用方式合法、合约允许或没有争议**。法律、平台条款、内容授权和司法实践会变化；重大或商业用途应咨询有执业资格且熟悉适用地区法律的专业人士。

## 使用前必须由用户自行确认

使用者应在每次下载、保存或自动处理内容前自行确认：

1. **内容授权**：自己是否获得了下载、复制、长期保存、转换格式或制作本地副本的许可；“可以在线观看”不当然等于“可以下载或另行复制”。
2. **平台条款**：当前 B 站用户协议、开发者规则及内容页面附加条件是否允许相应访问、自动化或下载方式。
3. **地区法律**：所在地及可能适用地区的著作权、合同、技术措施、数据保护、反不正当竞争和刑事法律要求。
4. **用途与范围**：是否仅为已获授权的个人用途；分享、上传、公开传播、商业利用、账号池或大规模自动化通常会引入额外风险。
5. **技术措施**：目标内容是否受 DRM、付费墙、访问控制或其他技术保护；本项目不应被用于规避这些措施。

如果无法确认授权或规则，最稳妥的做法是不下载、不自动处理，并使用平台提供的官方离线或收藏能力。

## 不作确定性法律结论

以下概念应分别判断，不能互相替代：

- 违反平台条款可能产生账号限制、服务终止或合同争议；
- 内容复制、格式转换、字幕/封面/弹幕保存可能涉及不同权利；
- 不公开传播并不自动消除复制、技术措施或合同问题；
- 使用自己的账号、有权观看或不盈利，也不自动证明下载行为获得授权；
- 开源、免费、免责声明或“仅供学习”标签都不构成法律豁免。

因此本文件不使用“基本不违法”“安全区”“低风险”“没有追责先例”等确定性表述，也不根据未核实个案推导普遍结论。

## 自动下载的技术约束

自动追更属于需要特别审慎评估的平台自动化场景。本项目用以下技术边界减少无意的高频请求，但这些边界**不是平台授权，也不构成合规证明**：

- UP 之间请求间隔 **≥ 5 秒**；
- 轮询间隔下限 **10 分钟**；
- 同一时刻只运行一轮；手动与定时触发必须先取得同一个非阻塞原子预约，进行中再次触发直接跳过、不排队补跑，也不改写上一轮状态；预约持续到本轮成功或错误终态状态写完；
- 只处理用户主动加入的 UP，添加时以当前最新投稿建立基线；
- 单轮每个 UP 最多 3 页；未跨过旧游标时保存 continuation，不把未扫描内容标为已见；首页漂移时持久化低页修复接缝，deep 已见末页/旧游标也必须等待接缝连续闭合后才推进 committed cursor；
- 同秒投稿使用时间戳 + BVID 集合游标；续扫累计最多 500 项，超限明确失败；
- 自动任务失败或进程中断后从持久任务史做指数退避，不用密集重扫恢复。

用户仍应根据账号、内容、平台通知和适用规则决定是否启用自动下载，并可随时移除 UP 或停止服务。

## 请求 governor 的准确范围

### 纳入保证的请求

本项目代码中**直接通过 `requests` 发出的 B 站 API/HTTP 调用**进入共享 governor：

- 单进程最多 2 个这类直接 HTTP 调用同时在途；
- `sensitive` 请求至少间隔 1.5 秒并加随机抖动；`bulk`、`media` 等类别使用各自间隔；
- 直接响应或显式 JSON 码为 412/429 时进入账号级冷却；合法 `Retry-After` 优先；
- 冷却期内本地接口快速返回 429，不继续由本项目直接 `requests` 调用轰炸上游；
- 登录来源切换不清账号冷却，避免把切换来源当作规避手段。

### 不纳入“两槽逐请求保证”的请求

解析和下载依赖 yt-dlp。每次 yt-dlp attempt 开始前，本项目会调用 governor 的 `wait("media")`，遵守当时的冷却和启动间隔；但是：

- **不能保证 yt-dlp 内部发出的每一个 HTTP 请求都经过本项目 governor**；
- yt-dlp 内部请求不占上述 2 个直接 `requests` 在途槽；
- 本项目 governor 不一定能逐个观察其响应中的 412/429、`Retry-After` 或计入指标；
- 下载并发另由全局下载 worker gate 控制，这与直接 HTTP governor 是两个不同边界。

因此不得把实现描述为“所有网络请求均受两槽 governor”。即使存在这些限频机制，也不能据此推断平台允许自动化访问。

## 认证、缓存与隐私边界

- 登录凭据、认证上下文、任务史、设置和页面缓存持久化在本机 `data/`；项目不设置自己的远端账号或遥测服务。
- 为完成登录、内容读取、解析和下载，必要请求与 Cookie 会发送给 B 站，yt-dlp 也会访问相应媒体地址；“本地应用”不等于“完全不与 B 站通信”。
- 页面缓存按账号 fingerprint、随机认证 incarnation 与生命期内 generation 分目录隔离；fingerprint 和 incarnation 都不是 Cookie，但可关联同一账号或本地认证生命期，应与其他运行数据一起妥善保护。
- 合法旧版认证状态迁移、状态缺失、损坏或凭据不可恢复都会开启新 incarnation；旧生命期缓存不回退复用。该隔离是工程边界，不表示凭据本身不会失效。
- 扫码凭据、导入 Cookie 和浏览器 Cookie 都可能失效；不得向他人提供或上传这些文件。
- 本机 Web 服务只接受 loopback Host，浏览器来源头存在时要求严格同源；这些措施降低本机接口被跨站调用的风险，但不替代操作系统账号安全和目录权限。
- 动态页面内容做转义、外部 URL 做协议限制；仍应把来自上游、文件和命令输出的内容视为不可信数据。

## 项目层面的技术护栏

1. 不提供账号池、代挂或绕过登录限制的功能；
2. 不实现 DRM、付费墙或技术保护规避；
3. 不提供上传、分享或二次分发入口；
4. 项目直接 `requests` 调用受并发、分类间隔和 412/429 冷却约束，自动追更另有 5 秒/UP 与 10 分钟轮询下限，并以原子非阻塞预约保证手动/定时触发不排队叠加；
5. 新任务使用稳定任务/产物身份和 manifest；创建先落任务记录再入队，取消写成功后才向 worker 发布，删除先持久化记录变化再处理已确认文件；
6. 批量、UP 清单、续扫、任务史、任务文件和 SSE 都有明确容量边界；
7. 认证请求、内存缓存和磁盘缓存按 fingerprint + incarnation + generation 隔离，账号、生命期或代际切换时旧请求不能提交到当前上下文；前端 status 与认证 mutation 分别使用独立 owner，迟到操作不得提示或清理较新的认证状态；
8. API 使用稳定错误码并隐藏内部异常；日志轮转且不应记录 Cookie。

这些是工程风险控制，不是法律判断或平台许可。

- 是否存在广告、收费、推广、账号池、多用户或跨地域服务；
- 收到平台、权利人或监管通知时的响应和证据保全流程。
